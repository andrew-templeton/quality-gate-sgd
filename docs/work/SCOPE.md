# Scope and completion evidence

The work graph covers the complete reusable Quality-SGD engine, its independently maintained example modules and the evidence needed to assess those examples. The minimum stable API milestone is one intermediate milestone. Tasks outside that path remain required work.

This audit extends the original 27-task graph to 36 tasks. The original task IDs and all original acceptance criteria are retained. Added dependencies connect later empirical work to the executable workflows it needs. An `active` status means implementation has begun; it is not evidence that a criterion passes.

## What the evidence may establish

Protocol tests establish behavior at the tested boundary. A structured source fixture can establish exact arithmetic, scope coverage and failure handling for its declared representation. An actual browser render can establish the measured geometry and interactions in its recorded view/state matrix. These are useful guarantees with bounded applicability.

Reader comprehension, operator preference and substantive verifier validity require observations appropriate to those claims. A runnable game with simulated ballots proves the game mechanics. It does not prove that an operator prefers the resulting composition. An independent simulated-reader study can provide empirical evidence about that specified model and restricted reader context, provided the study records its protocol, model identity, artifacts, actual responses, labels and uncertainty. It cannot establish performance for human readers by relabeling the result.

No task requires inventing evidence or obtaining a favorable result. A fixed study that exposes failure or uncertainty can complete an evaluation task when all required observations and analysis are present. It leaves the evaluated assertion or composition unqualified whenever its acceptance threshold was not met. Preparing a protocol without running its required observations is incomplete evaluation work.

Some claims could require additional human participation or independently sourced labels. If such a claim is selected, record the needed population and evidence before collecting outcomes, keep the claim unqualified while those observations are absent, and continue implementation or other scoped studies in parallel. Do not silently replace a human claim with a model simulation, or portray test-participant ballots as the user's own choices.

## Privacy and publication boundary

Portable examples use synthetic or explicitly publishable source material. The public graph does not require publishing recovered conversations, named readers, private client documents or private planning records. Module implementations and their public evidence belong to the declared owning repositories. Isogloss remains an external facet rather than a bundled core implementation.

## Completion procedure

For each task, inspect its exact acceptance criteria in [graph.json](./graph.json), identify the source or runtime evidence that could prove each criterion, run or inspect that evidence at the final relevant revision, and record limitations alongside results. A link, green check or card declaration does not authenticate the claim by itself.

Only mark a task done after that review and after all its prerequisites are done. Regenerate [README.md](./README.md) with `npm run plan:generate`, then validate with `npm run plan:check`. The final audit covers all tasks and public repository outcomes; completing only `stable-api-review` does not finish the graph.
